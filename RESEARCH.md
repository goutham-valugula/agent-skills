### Current candidates (hypotheses; order is provisional and must be compared against new cross-domain discoveries)

1. **Design-to-ship reviewer (anchor skill):** Inspect an existing project and user brief; establish a specific art direction; reuse its actual stack/tokens; implement a coherent screen; render it in a real browser at desktop/mobile; catch regressions; return screenshots and a prioritized evidence-based QA report. Inspiration: Taste Skill, UI UX Pro Max. Differentiator to pursue: a portable, inspectable workflow with before/after evidence, restrained scope, accessibility checks, and explicit "what I could not verify" output—not another style catalog.
2. **Voice UI architect and QA:** Turn a product's conversation requirements into a provider-neutral interaction/state model, then implement and review the voice surface. Cover permission denied, connecting, listening, thinking, speaking, interruption/barge-in, mute, transcript, reconnect, errors, keyboard/screen-reader access, reduced motion, and typed fallback. Document transport/media ownership and provider-specific differences; keep credentials server-side and never let raw transcripts authorize privileged actions. Inspiration: ElevenLabs Speech Engine and orb-ui provider comparison. Differentiator: a state-transition matrix plus browser-test checklist that covers failures, not a decorative orb recipe.
3. **Accessibility repair with proof:** Audit a chosen flow against WCAG 2.2 AA expectations, reproduce issues, make narrow fixes using existing patterns, and give keyboard/screen-reader/zoom/contrast verification evidence. Do not claim certification or conformance from a heuristic scan.
4. **Figma-to-code fidelity:** Read provided Figma nodes/assets and the repository's real components/tokens; identify unknowns; implement the selected frame responsively; compare browser screenshots against reference at matching viewport; report deviations. Inspiration: official Figma skills indexed by VoltAgent and design-build workflows in jakubkrehel/skills. Do not invent Figma access or claim pixel perfection without visual comparison.
5. **Design-system drift detective:** Compare changed UI against the project's own tokens/components and documented interaction patterns; locate hard-coded or divergent values; propose/fix a small batch and produce a drift report. Avoid imposing a new system or global redesign.
6. **UI bug reproducer and regression harness:** Convert a screenshot/description into a minimal reproducible case, inspect console/network, fix one root cause, then verify the exact route and nearby responsive/accessibility states. The output is reproduction steps, root cause evidence, changed behavior, and remaining uncertainty.
7. **Agent skill quality lab:** Evaluate a skill on representative tasks with/without the skill, observable acceptance criteria, failure cases, token/cost/time overhead where available, and versioned results. A skill is promoted based on measurable improvement and safe operation, not length or stars.

**Recommendation:** Do not assume any candidate here should be built next. At each research synthesis, compare the best new opportunity from any domain against this list using a documented scorecard (user pain/evidence, expected impact, repetition, alternatives gap, feasibility, verification quality, portability, and risk). Build only the current best candidate after the quality gate; derive focused skills only where their jobs are genuinely distinct. #7 can serve as internal infrastructure, but it too should be evaluated for value versus overhead.

**Quality gate for each candidate:** (a) define an exact user and job; (b) inspect at least three current, independent primary references or real user examples; (c) describe alternatives and what they fail to do; (d) create at least two realistic fixture tasks including a failure/edge case; (e) specify observable acceptance criteria and tool prerequisites; (f) test with a baseline and skill-assisted run before calling it effective; (g) identify secret, privacy, external-action, and destructive-operation boundaries; (h) include an honest install/use example and license/attribution review. No star target substitutes for this gate.

**Decision:** Keep the existing generic skills in place for now; do not bulk-delete or rename them. Treat them as legacy starter workflows pending comparative evaluation. Update this roadmap when new evidence changes priority. Do not promise highest stars—focus on clear positioning, quality, distribution, and user outcomes.

## 2026-11-17 — Starter-kit selection and format

- OpenAI's official [Skills guide](https://openai.com/academy/skills/) describes skills as repeatable workflows with a clear job, inputs, outputs, and guardrails. It recommends small building blocks and splitting unrelated work instead of making one oversized skill.
- OpenAI's [API skills documentation](https://developers.openai.com/api/docs/guides/tools-skills) says skills use a `SKILL.md` manifest with front matter and instructions and are compatible with the open Agent Skills standard. Product-specific installation still varies, so this repo does not claim automatic installation across every assistant.
- Based on those design principles, the first starter kit covers distinct common jobs: triaging messages, preparing/following up meetings, comparing choices, planning a week, drafting replies, shopping research, truthful job applications, safe troubleshooting, learning, and trip planning. This selection is a usefulness hypothesis, not a measured ranking or proof of demand.
- Every workflow is designed to produce a reviewable draft or plan. It must not imply that it sent, booked, purchased, applied, edited, or otherwise changed anything unless a user explicitly authorizes a connected tool action.
- **Decision:** Publish the starter kit as practical drafts, clearly label demand as unvalidated, and gather user feedback before claiming any individual skill is proven or adding features for popularity alone.

## Initial direction

## Format and quality evidence

- The [Open Agent Skills specification](https://openagentskills.dev/docs/specification) defines a skill as a folder with a `SKILL.md` file, required `name` and `description` fields, and optional supporting references/scripts. It recommends keeping the main instructions concise and validating the format.
- [OpenAI's Skills documentation](https://developers.openai.com/api/docs/guides/tools-skills) describes skills as reusable instructions plus supporting files and says they are compatible with the open Agent Skills standard. Product-specific installation still needs to be checked before being documented.
- A 2026 study, [After the Party: Governing What a Viral Agent-Skill Ecosystem Left Behind](https://arxiv.org/abs/2609.17274), reports that popularity signals were not reliable quality measures in its study window and that the skills ecosystem carried meaningful privilege/security risks. This is a reason to prioritize review, transparent limitations, and safe-by-default instructions—not to chase stars alone.
- A third-party leaderboard currently shows many large skill repositories centered on software development, design, and security. Treat its counts/rankings as a changing snapshot, not verified demand or proof that another broad bundle will succeed: [Skill Leaderboard](https://www.skillleaderboard.com/).

## First candidate: document to next steps

**User problem hypothesis:** A person receives a long or unfamiliar document and cannot quickly tell what it asks them to do.

**Proposed result:** A short plain-language summary; action checklist; dates copied exactly from the source; unfamiliar terms explained; unclear/missing information called out; and page/heading references where available.

**Guardrails:** Never invent a deadline or obligation, silently omit uncertainty, make a legal/medical/financial decision, or send the document to a service. The skill should work on user-provided text/files only and remind users to verify important details against the original.

**Evidence still needed:** Find independent examples across different kinds of users/documents; identify a specific gap beyond existing document assistants; test with representative sample documents; record failures and revise. Do not describe the problem as validated until that work is complete.
